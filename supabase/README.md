# supabase/: серверная часть каталога GDS «Джедес»

Серверная часть состоит из SQL для Supabase (PostgreSQL, Auth, Storage, RLS). Кода сервера нет: REST создаёт сам Supabase. Контракт: `docs/api.md`. Решение и найденные в ТЗ расхождения: `docs/adr/0001-supabase-backend.md`. Что должен сделать владелец: `HUMAN_ACTIONS.md` (в корне репозитория).

## Содержимое

| Путь | Что это |
|---|---|
| `migrations/001_init.sql` | расширение, 6 таблиц, ограничения значений, индексы, триггер `updated_at`; таблицы создаются закрытыми (RLS без политик) |
| `migrations/002_rls.sql` | функция `is_admin()`, явные права ролей, политики RLS, самопроверка с откатом (сверка списка политик) |
| `migrations/003_storage.sql` | бакеты `product-images` и `brand-logos` (часть 1), политики Storage и самопроверка (часть 2) |
| `migrations/004_seed.sql` | бренд, категория, 10 вкусов Stellar, точка продаж (начальный контент) |
| `tests/` | **не для Supabase:** заглушка Supabase и SQL-тесты для одноразовой базы, см. `tests/README.md` |

## Порядок и применение

Файлы выполняются строго по номерам, каждый целиком, в Supabase SQL Editor (шаги для владельца: `HUMAN_ACTIONS.md`, Шаг 3). Каждый файл можно запустить повторно: он ничего не дублирует, не удаляет данные и (`001`) не отнимает права, выданные `002`. Оговорки: `004` ищет строки по ключам (имя бренда, slug, название и адрес точки), поэтому после переименования ключа повтор вернёт строку под старым ключом; самопроверки `002` и `003` останавливают повтор, если в проекте есть посторонние политики (после добавления новых политик следующими миграциями список разрешённых в самопроверке нужно обновить). `003` состоит из двух транзакций: бакеты и политики. Миграции только добавляют; удаления и переименования делаются отдельным релизом по решению владельца.

Если репозиторий станет публичным: в `supabase/`, `docs/` и `HUMAN_ACTIONS.md` описана конфигурация защиты, а в `004_seed.sql` и документах лежит рабочая почта точки продаж (из ТЗ). Решите заранее, можно ли это публиковать.

Нумерация: в ТЗ seed назван `003_seed.sql`, но там же Storage идёт перед ним; чтобы номера не повторялись, Storage получил `003`, seed `004`.

Совместимость с Supabase CLI (`supabase db push`): имена `NNN_название.sql` принимаются как версии 001-004. Если позже начнёте использовать CLI, новые миграции создавайте через `supabase migration new`: они получат временные метки, которые больше этих номеров.

## Правила

- В этих файлах нет секретов, паролей и ключей, и быть не должно.
- Таблицы в `public` нового проекта и старого ведут себя по-разному (права по умолчанию); любая новая таблица сразу получает `enable row level security`, явные `grant` и политики (образец: `001_init.sql` и `002_rls.sql`).
- Служебные колонки в публичные таблицы не добавлять (`docs/api.md`, «Правила изменения контракта»).
- Файлы из `tests/` в Supabase не выполнять.
