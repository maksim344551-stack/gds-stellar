# supabase/tests/: проверки миграций на одноразовой базе

**Это не Supabase и не для боевой базы.** Здесь лежит заглушка окружения Supabase (`shim.sql`) и SQL-тесты. Они нужны, чтобы проверить миграции из `../migrations` на обычном одноразовом PostgreSQL. Заглушка лишь похожа на настоящий Supabase; поведение настоящего Supabase она не доказывает.

## Что внутри

| Файл | Что делает |
|---|---|
| `shim.sql` | поддельные роли `anon`, `authenticated`, `service_role`, схемы `auth` и `storage`, `auth.users`, `auth.uid()`, `storage.buckets`, `storage.objects`; права по умолчанию как в старых проектах Supabase. Защищён от запуска на настоящей базе (см. начало файла) |
| `shim_strict_defaults.sql` | то же, но в «новом» режиме платформы: новые таблицы и функции ролям автоматически не выдаются |
| `sql/00_helpers.sql` | функция `gds_test.check()`, печатает строки `RESULT\|id\|PASS\|FAIL\|описание` |
| `sql/window/01_after_001.test.sql` | состояние сразу после `001` (до `002`): таблицы закрыты в обоих режимах платформы |
| `sql/10_structure.test.sql` | колонки и типы как в ТЗ, ключи, `on delete`, ограничения значений (в том числе NaN, пробельные строки, ссылки, e-mail), индексы, триггер, функции, права на таблицы и колонки, точный набор политик |
| `sql/20_access_matrix.test.sql` | аноним, обычный вошедший, админ, поддельный токен: чтение, запись, `ON CONFLICT`, `FOR UPDATE`, видимость скрытых строк, `user_roles` |
| `sql/30_storage.test.sql` | настройки бакетов, политики `storage.objects`, правила имён файлов, бакеты нельзя создавать |
| `sql/40_seed.test.sql` | содержимое сида совпадает с ТЗ, порядок вкусов; нет пользователей и ролей; нейтральность текстов (эвристика) |
| `run.mjs` | четыре круга (см. ниже), сверка с манифестом |
| `expected-checks.txt` | манифест: полный список идентификаторов проверок (376). Удалённая или новая проверка без обновления манифеста даёт провал |
| `lib/sandbox.mjs` | запуск одноразового кластера `embedded-postgres`; проверка имён, версий и sha256 входных файлов пакетов перед загрузкой |
| `sandbox-embedded.mjs` | поднимает одноразовый PostgreSQL без Docker и вызывает `run.mjs` в обоих режимах прав |
| `mutations.mjs` | мутационная проверка: 44 намеренные поломки (36 состояния базы и 8 исходников миграций), каждая должна покраснеть хотя бы в одной проверке |

## Круги `run.mjs`

1. Круг 1: сначала только `001` и тесты «окна»; потом остальные миграции, тесты `sql/*.test.sql` и SQL-блоки из `docs/backend-security-checklist.md` (помеченные `-- check:<id>`; для них создаётся временный админ).
2. Круг 2: все миграции повторно (идемпотентность), снова тесты и блоки чек-листа.
3. Круг 3: повторно только `001` (он не должен отнимать права, выданные `002`), снова тесты и блоки.
4. Круг 4: повтор сида не затирает правки админа (`R01`–`R03`); самопроверки `002` и `003` сами останавливают файл, когда защита испорчена (`SC01`–`SC07`).
5. Сверка: набор проверок в кругах 2 и 3 совпадает с кругом 1; полный набор совпадает с манифестом.

## Защита от ошибки «не туда»

- `run.mjs` отказывается работать, если адрес базы не локальный (`localhost`, `127.0.0.1`, `::1`) или в имени базы нет отдельным словом (через `_` или `-`) `test`, `dev`, `tmp`, `sandbox`. Строку подключения он не печатает.
- `shim.sql` дополнительно требует в имени базы `test`, `sandbox` или `tmp`, а также особое значение настройки `gds.sandbox_ack`, которое ставит только `run.mjs`. В настоящем Supabase файл остановится и на самой первой команде, потому что схемы `auth` и `storage` там уже есть.
- Тесты открывают транзакцию и в конце откатывают её.
- Драйвер `pg` и пакет `embedded-postgres` грузятся из папки вне проекта (`GDS_SANDBOX_PREFIX`, `GDS_PG_MODULE`) только если имя, версия и sha256 входных файлов пакета совпадают с закреплёнными в `lib/sandbox.mjs` (`PINNED`, `ENTRY_HASHES`); остальные файлы пакета не проверяются, поэтому папка должна быть вашей, созданной командой из этого файла.
- В тестах нет динамического SQL (`execute`) и нет вызова оболочки: операторы пишутся явно, значения передаются параметрами.

## Как запускать

**Вариант 1: без Docker (так запускал я).** Пакеты ставятся вне проекта, `package.json` проекта не меняется. Путь в `GDS_SANDBOX_PREFIX` абсолютный:

```powershell
npm.cmd install --prefix C:\temp\gds-pg --save-exact --ignore-scripts embedded-postgres@17.10.0-beta.17 @embedded-postgres/windows-x64@17.10.0-beta.17 pg@8.23.1
$env:GDS_SANDBOX_PREFIX = "C:\temp\gds-pg"
node supabase/tests/sandbox-embedded.mjs
node supabase/tests/mutations.mjs
```

Для PostgreSQL 15 поставьте `embedded-postgres@15.18.0-beta.17` и `@embedded-postgres/windows-x64@15.18.0-beta.17` в другую папку. На другой ОС замените платформенный пакет. Дополнительные параметры `sandbox-embedded.mjs`: `--variants=legacy,strict`, `--locale="English_United States.1252"` (локаль, близкая к `en_US.UTF-8`; по умолчанию `C`), `--no-docs`, `--update-manifest` (после намеренного изменения набора проверок). Данные кластера лежат во временной папке и удаляются; порт выбирается свободный; пароль случайный.

**Вариант 2: Docker.** Любой одноразовый PostgreSQL 15 или новее, например контейнер на порту `55432` с базой `gds_x_test` (пароль придумайте и не сохраняйте), затем:

```powershell
$env:DATABASE_URL = "postgres://postgres:<пароль>@127.0.0.1:55432/gds_x_test"
$env:GDS_PG_MODULE = "C:\temp\gds-pg\node_modules\pg"   # драйвер pg, установленный вне проекта
node supabase/tests/run.mjs --variant=legacy
node supabase/tests/run.mjs --variant=strict   # нужна ПУСТАЯ база: создайте вторую одноразовую
```

Код выхода 0: всё прошло; 1: есть провалы (в выводе строки `ПРОВАЛ …`); 2: неверный запуск.

Каждый режим прав прогоняется на отдельной пустой базе, потому что `shim.sql` создаёт схемы без `if not exists` (так он не запустится на настоящей базе).

## Как добавить проверку

1. Новый `sql/NN_название.test.sql`: `begin;` … `rollback;`, внутри блоки `do $$ … $$;`, результат через `perform gds_test.check('ID', условие, 'описание');`.
2. Вход под ролью имитируется так: `perform set_config('request.jwt.claims', '{"sub":"<uuid>","role":"authenticated"}', true); set local role authenticated;` … `reset role;` (всегда возвращайте роль до вызова `gds_test.check`).
3. После любой правки политик, прав, ограничений или набора проверок прогоните оба режима, обе версии PostgreSQL и `mutations.mjs`; затем обновите манифест (`--update-manifest`) и проверьте его диф.
4. Новую защиту сопровождайте новой «поломкой» в `mutations.mjs`: если её нельзя сломать так, чтобы что-то покраснело, проверка пустая.

## Что тесты НЕ доказывают

Настоящий PostgREST и коды HTTP-ответов; GoTrue (регистрация, вход, подтверждение почты); Storage API (лимиты размера и типов, публичные ссылки); роль `postgres` без суперправ и точные права владельца на `storage.objects`; поведение SQL Editor; настройки панели; Security Advisor; резервные копии. Эти пункты проверяются руками по `docs/backend-security-checklist.md` на живом проекте.

В пакете `embedded-postgres` нет `psql` и `pg_dump`, поэтому восстановление из копии здесь не проверялось.
