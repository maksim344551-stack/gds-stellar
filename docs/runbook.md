# Ранбук: что делать, если что-то случилось (бэкенд GDS на Supabase)

Версия 2026-10-08. Короткие инструкции для владельца. SQL выполняется в Supabase: **SQL Editor → New query → Run**. Названия пунктов панели иногда меняются: ищите по смыслу. Эти сценарии я на живом проекте не проверял (проекта пока нет).

## 1. Срочно убрать весь каталог с сайта (и вернуть)

Скрытие действует сразу для публичного ключа: бренд, его вкусы и записи о картинках перестают отдаваться через API (чек-лист, пункт 8). Данные не удаляются.

```sql
update public.brands set is_active = false where name = 'GDS Джедес';
```

Вернуть:

```sql
update public.brands set is_active = true where name = 'GDS Джедес';
```

Один вкус: `update public.products set is_active = false where slug = 'altair';` (вернуть: `true`). Одну точку продаж: `update public.stores set is_active = false where name = '…';`.

Сайт может показывать кэшированные копии у посетителей; сама база отдаёт новое состояние сразу.

**Это скрывает только строки базы, а не файлы.** Картинки в публичных бакетах продолжают открываться по прямым ссылкам, пока файлы лежат в Storage, и ещё какое-то время из кэша CDN (срок я не проверял). Если нужно убрать и файлы:

1. Закрыть публичный доступ к файлам бакетов (ссылки перестанут открываться; после кэша CDN):

```sql
update storage.buckets set public = false where id in ('product-images', 'brand-logos');
```

   Вернуть: тот же запрос с `public = true` (повторный запуск `003_storage.sql` тоже вернёт `public = true`). После выполнения откройте любую ссылку на файл в браузере без входа и убедитесь, что она больше не открывается (поведение Storage я на живом проекте не проверял).
2. Для окончательного удаления: **Storage → бакет → выбрать файлы → Delete** (по моим сведениям, из SQL удалять строки `storage.objects` нельзя, Storage это блокирует; не проверялось). Файлы вкуса не удаляются вместе со строкой вкуса.

Оговорка: если когда-нибудь админка будет выдавать подписанные ссылки на загрузку, уже выданная ссылка может продолжать работать до истечения срока (по документации Storage это часы; не проверялось), даже после снятия роли или закрытия бакета.

## 2. Подозрение, что взломан аккаунт админа

Порядок (каждый шаг можно делать отдельно):

1. Снять роль: `delete from public.user_roles where id = '<UUID админа>';`. Роль берётся из таблицы при каждом запросе (не из токена), поэтому запись в каталог для этого пользователя закрывается **сразу**, даже если у него остался действующий вход.
2. **Authentication → Users**: найти пользователя, сменить пароль или удалить его (удаление автоматически удаляет и строку роли).
3. Проверить, что изменилось в каталоге. У `products` есть дата изменения: `select slug, name, updated_at from public.products order by updated_at desc nulls last limit 20;`. Для остальных таблиц даты изменения нет (журнала действий админа в этой версии нет, см. ADR, остаточный риск 1): сверьтесь с `supabase/migrations/004_seed.sql` и с вашей памятью.
4. Если каталог испорчен: восстановить правки из копии (раздел 6) или вернуть стартовое состояние (раздел 7).
5. Создать нового админа по шагу 5 из `HUMAN_ACTIONS.md`.

## 3. Утечка ключа

- **Публичный ключ** (`sb_publishable_…` или `anon`): он публичный по замыслу, это не утечка. Защита держится на правах и политиках.
- **Секретный ключ** (`sb_secret_…`) или `service_role`: обходит все политики. Если он попал в код сайта, в чат, в репозиторий: **Project Settings → API Keys**, создайте новый секретный ключ, затем удалите старый (для старых ключей `service_role` отключите legacy-ключи или поменяйте JWT-секрет в настройках; пункты называются по-разному в разных версиях панели). Заменить ключ придётся везде, где он использовался. Сообщите мне: проверю, не осталось ли его в истории git.
- **Пароль базы данных**: **Project Settings → Database → Reset database password**. Сайту он не нужен.

## 4. Админ забыл пароль

Письмо для сброса пароля, пока не настроена собственная почтовая служба, ненадёжно. Варианты: в **Authentication → Users** в меню пользователя поменять пароль (если такой пункт есть); иначе создать нового пользователя (шаг 5 в `HUMAN_ACTIONS.md`), выдать ему роль, а старого удалить.

## 5. Сайт получает ошибки или пустые ответы

1. Откройте панель проекта. Если проект **приостановлен** (бесплатный тариф при низкой активности за 7 дней): кнопка **Restore project**, подождать несколько минут.
2. Проверьте статус платформы на странице статуса Supabase.
3. Если проект работает, а ответы пустые: выполните в SQL Editor `select count(*) from public.products;`. Ноль значит, что данных нет (раздел 7). Ненулевое число, но пустой ответ сайта значит, что вкусы или бренд скрыты (`is_active = false`, раздел 1) или в запросе нет публичного ключа.
4. Выполните пункт 7 чек-листа (сводка защиты): он быстро покажет, не сломаны ли права.
5. Если сайт имеет резервные данные в `src/data.js`, решение показывать их при ошибке API принимается в сессии сайта.

## 6. Восстановление из резервной копии

- **Платный тариф:** панель **Database → Backups**, ежедневные копии (7 дней), по желанию точка во времени (дополнительная услуга). Восстановление заменяет текущее состояние базы: перед ним сохраните то, что менялось после копии.
- **Free:** автоматических копий нет. Структура и стартовое содержимое восстанавливаются из файлов 001-004. Свои правки восстанавливаются только из ваших выгрузок (`supabase db dump --data-only`, см. HUMAN_ACTIONS.md, шаг 9).
- После любого восстановления выполните пункты 1, 2 и 7 чек-листа.
- Проверка восстановления из копии на этом проекте не проводилась (копий ещё нет).

## 7. Вернуть стартовое содержимое (удалены или испорчены строки)

`004_seed.sql` можно запускать снова: он **добавит только отсутствующие** строки (бренд, категорию, вкусы по slug, точку) и **не изменит** существующие, то есть не откатит ваши правки. Ограничения:

- Чтобы вернуть исходный текст одного вкуса, удалите его строку (`delete from public.products where slug = '…';`) и запустите `004_seed.sql` снова. **Удаление вкуса каскадно удаляет его записи о картинках в `product_images`** (файлы в Storage остаются), а вернувшаяся строка получит новый идентификатор; записи о картинках придётся завести заново.
- Строки ищутся по ключам: бренд по имени, категория и вкус по `slug`, точка по названию и адресу. Если вы **переименовали** ключ (например, `slug` у Isida на `auris`), повторный запуск добавит строку под старым ключом: вкусов станет 11. Перед повторным запуском приведите тексты в `004_seed.sql` в соответствие с вашими правками или не запускайте его.

## 8. Нужна новая версия схемы

Миграции только вперёд: добавьте файл `005_…sql` рядом с остальными (сначала добавляем, потом переводим сайт, удаляем отдельным релизом). Откатить миграцию назад SQL-файлом я не делаю: до наполнения боевыми данными проще создать проект заново, после наполнения нужна новая миграция вперёд. Любые удаления и переименования на живой базе выполняет владелец после моего описания шагов.

## 9. Всплеск запросов или подозрительная активность

Каталог читается публично по замыслу, поэтому всплеск чтения сам по себе не взлом. Смотрите **Reports** в панели. Крайняя мера: создать новый публичный ключ в **Project Settings → API Keys** и удалить старый (старый перестанет работать у всех, сайт надо будет обновить новым). Лимиты на вход (брутфорс пароля админа) настраиваются в **Authentication → Rate Limits**; при необходимости включите защиту CAPTCHA (решение владельца, потребует подключения сервиса).

## 10. Запасной путь: политики Storage через панель

Нужен, только если часть 2 файла `003_storage.sql` остановилась с «must be owner of table objects» (у SQL Editor нет права создавать политики на таблице Storage). Бакеты к этому моменту уже созданы частью 1 файла (она применяется отдельно) и без политик безопасны: загрузить файл и получить список нельзя, а файлы открываются по публичной ссылке.

В панели: **Storage → Policies** (или **Authentication → Policies**, схема `storage`, таблица `objects`) → **New policy** → **For full customization**. Создайте четыре политики, роль везде **authenticated**:

| Имя | Операция | USING | WITH CHECK |
|---|---|---|---|
| `gds_storage_admin_read` | SELECT | `bucket_id in ('product-images', 'brand-logos') and (select public.is_admin())` | пусто |
| `gds_storage_admin_insert` | INSERT | пусто | выражение «имя файла» ниже |
| `gds_storage_admin_update` | UPDATE | `bucket_id in ('product-images', 'brand-logos') and (select public.is_admin())` | выражение «имя файла» ниже |
| `gds_storage_admin_delete` | DELETE | `bucket_id in ('product-images', 'brand-logos') and (select public.is_admin())` | пусто |

Выражение «имя файла» (одна строка, для INSERT и UPDATE):

```
(select public.is_admin()) and ((bucket_id = 'product-images' and name ~ '^[a-z0-9]+(-[a-z0-9]+)*/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.(jpg|jpeg|png|webp|avif)$') or (bucket_id = 'brand-logos' and name ~ '^gds/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}\.(jpg|jpeg|png|webp|avif)$'))
```

Эти выражения должны совпадать с `003_storage.sql`, часть 2 (при расхождении верен файл). Политики для `anon` и для публичной роли **не создавайте**. После создания выполните пункты 4 и 7 чек-листа: они подтвердят, что политики на месте и чужих нет. Этот путь я на живом проекте не проверял.
