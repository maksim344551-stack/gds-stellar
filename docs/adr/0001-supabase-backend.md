# ADR-0001: Серверная часть каталога GDS «Джедес» на Supabase

Дата: 2026-10-08, обновлено 2026-10-09 (правки по двум независимым ревью).
Статус: **принято владельцем по ТЗ от 2026-10-08** в части платформы, таблиц, политик и порядка миграций (их задал владелец). **Отступления от ТЗ и допущения, перечисленные ниже, владельцем ещё не подтверждены**: они вынесены в раздел «Нужно решение владельца».

## Контекст

- Сайт GDS Stellar (Vite и three.js) сейчас статичный, серверной части нет (README). Все вкусы лежат в `src/data.js`. Владелец хочет справочник продукции в базе, чтобы править каталог без пересборки сайта.
- Сайт информационный: по утверждению владельца в ТЗ он подпадает под ограничения закона о табачной продукции (в ТЗ названа ст. 27 закона 15-ФЗ). **Я эту ссылку не проверял и не утверждаю её как факт: это вопрос юристу** (HUMAN_ACTIONS.md). Поэтому в базе нет цен, заказов и корзины, а описания вкусов только нейтральные (характеристики ароматического профиля).
- Сайт обращается к базе с публичным ключом, который виден любому посетителю. Значит, вся защита данных находится в самой базе: права ролей и политики построчной защиты (RLS).
- Единственный пользователь с правами записи: владелец (роль `admin`).

## Решение

Supabase: PostgreSQL, Auth (почта и пароль), Storage, RLS. Сайт читает каталог через автоматический REST (PostgREST) с публичным ключом. Своего сервера нет. Схема задаётся четырьмя SQL-миграциями в `supabase/migrations`, которые владелец выполняет по очереди в SQL Editor:

| Файл | Что делает |
|---|---|
| `001_init.sql` | расширение, 6 таблиц, ограничения значений, индексы, триггер `updated_at`; таблицы сразу закрыты: RLS включён без политик, служебные права отозваны |
| `002_rls.sql` | функция `is_admin()`, явные права ролей, политики RLS, самопроверка итога с откатом (в том числе сверка полного списка политик) |
| `003_storage.sql` | часть 1: два публичных бакета с лимитами; часть 2 (отдельной транзакцией): политики Storage только для админа и самопроверка |
| `004_seed.sql` | бренд, категория, 10 вкусов Stellar, точка продаж; повторный запуск не дублирует и не затирает правки |

Вспомогательное: `supabase/tests` (заглушка Supabase для одноразовой базы, SQL-тесты, `run.mjs`, `sandbox-embedded.mjs`, `mutations.mjs`), `docs/api.md`, `docs/backend-security-checklist.md`, `docs/runbook.md`, `HUMAN_ACTIONS.md`.

## Альтернативы и почему не они

- **Свой сервер (Express или Next.js) с Postgres.** Для справочника с одним админом это лишний хостинг, лишний код и лишняя поверхность атаки. Выбор владельца в ТЗ: Supabase.
- **Оставить данные в `src/data.js`.** Проще и без внешней зависимости, но правка вкуса требует пересборки и выкладки сайта. Файл остаётся хорошим резервом (запасной вариант на случай недоступности API), решение для сайтовой сессии.
- **Supabase CLI (`supabase db push`).** Удобнее для разработчика, но требует установки программ и доступа к проекту. Нетехническому владельцу проще SQL Editor. Файлы с номерами `001_`, `002_` совместимы с CLI на случай перехода.

## Сверка ТЗ: найденные противоречия, пробелы и небезопасные места

Что в ТЗ расходится само с собой, чего в нём не хватает и что я сделал. Решения по умолчанию записаны здесь как допущения; то, что решает владелец, вынесено в конец.

| # | Место в ТЗ | Проблема | Что сделано |
|---|---|---|---|
| 1 | Политики «SELECT только `is_active = true`» для всех пяти таблиц | У `categories` и `product_images` колонки `is_active` нет, политику в таком виде записать нельзя | `categories`: читают все строки (в ней нет скрываемого содержимого). `product_images`: картинка видна, только если виден её вкус (вкус и бренд активны); иначе ссылки на картинки скрытых вкусов утекали бы через API |
| 2 | ТЗ молчит про вкусы скрытого бренда | Скрыли бренд, а вкусы остались публичными, у них «пустой» бренд | Вкус публично виден, только если активен и он, и его бренд. Это строже ТЗ и согласуется с «только `is_active = true`». Вернуть как в ТЗ можно одной политикой (ниже) |
| 3 | `on delete cascade` у `products.brand_id` и `products.category_id` | Случайное удаление бренда или категории молча стирало бы все вкусы и картинки | `on delete restrict`: удаление отклоняется (23503), вкус скрывают через `is_active`. Каскад оставлен там, где он безопасен: `product_images` от вкуса, `user_roles` от пользователя Auth. **Отступление от ТЗ** |
| 4 | `SECURITY DEFINER`-функция `public.is_admin()` | ТЗ не задаёт `search_path` и права вызова; функция в схеме `public` вызываема через REST | `set search_path = ''`, все имена с префиксом схемы, обработан пустой `auth.uid()`; право вызова только у `authenticated`, у `anon` и PUBLIC отозвано. Возвращает только статус самого вызывающего. Остаётся ожидаемым предупреждением Security Advisor |
| 5 | Права ролей на новые таблицы не упомянуты | До 30.05.2026 Supabase выдаёт `anon`, `authenticated`, `service_role` полный набор прав на новые таблицы `public` (включая `TRUNCATE`, который RLS не ограничивает). В проектах, созданных позже, права не выдаются вообще, и без явных `GRANT` сайт получит пустые ответы | `001`: RLS включён без политик (всё запрещено), служебные права `TRUNCATE`, `REFERENCES`, `TRIGGER` отозваны; `002`: права отзываются целиком и выдаются явно. Итог для `anon` и `authenticated` одинаков в обоих режимах платформы; состояние между `001` и `002` проверено отдельным тестом в обоих режимах |
| 6 | Storage: «SELECT: всем» на `storage.objects` | Публичная ссылка работает и без политики. Политика чтения для `anon` даёт любому владельцу публичного ключа **список всех файлов бакета**, в том числе ещё не опубликованные | Политики чтения для `anon` нет, ссылки работают по флагу `public`. Список файлов и перезапись файла разрешены админу. **Отступление от ТЗ**; проверка: пункт 4 чек-листа. Это центральное допущение о поведении Storage, подтверждается документацией Supabase, но **на живом проекте не проверено** |
| 7 | Бакеты без лимитов | Админский аккаунт мог бы залить файл любого типа и размера (SVG и HTML с публичного домена Supabase) | `file_size_limit`: 5 МиБ (картинки вкусов), 2 МиБ (логотипы); разрешены только `image/jpeg`, `image/png`, `image/webp`, `image/avif` |
| 8 | «Соглашение о путях» без проверки | Соглашение, которое ничем не проверяется, нарушается | Политики вставки и изменения принимают только пути `product-images/<slug>/<uuid>.<ext>` и `brand-logos/gds/<uuid>.<ext>` |
| 9 | Auth: почта и пароль, подтверждение почты выключить, роль выдаётся «после регистрации админа» | Открытая регистрация без подтверждения почты: любой создаёт аккаунт (роль `authenticated`, прав записи нет), а до вас может занять ваш адрес, и вы по ошибке выдадите роль его аккаунту | Рекомендация: закрыть регистрацию (Allow new users to sign up: выкл.), админа создать в панели Authentication → Users → Add user. Настройка вне SQL, шаги в HUMAN_ACTIONS.md. **Нужно решение владельца (вопрос 2)** |
| 10 | Ограничения значений не заданы | Мусор в slug, ссылках, e-mail и координатах | Именованные CHECK: формат slug; длины текстов и «не из одних пробельных знаков»; ссылка только `https` и только знаки `A-Za-z0-9._~:/?#%&=+-`; e-mail латиницей без кавычек, `< > & ; \`; координаты в диапазоне (NaN и бесконечность отклоняются); формат телефона; вес от 0,01, крепость от 0 (`between` отвергает и NaN, у `numeric` он иначе проходит «> 0») |
| 11 | Индекс `products(slug)` отдельно от `unique` | Дубль индекса, который уже создаёт `unique` | Второй индекс не создаётся; тест проверяет, что индекс по slug есть |
| 12 | `pgcrypto` для `gen_random_uuid()` | `gen_random_uuid()` встроена в PostgreSQL с версии 13; расширение в схеме `public` сделало бы `crypt`, `digest` вызываемыми через REST | Расширение подключено, как просит ТЗ, но в схему `extensions` |
| 13 | Порядок файлов: Storage назван «миграцией», seed назван `003_seed.sql` | Два файла претендуют на номер 003; Storage при этом идёт перед seed | `003_storage.sql`, `004_seed.sql`. Только номер, содержимое по ТЗ |
| 14 | «anon key» | У проектов, созданных после ноября 2025, публичный ключ называется publishable (`sb_publishable_…`), секретный `sb_secret_…`; старые `anon` и `service_role` Supabase выводит из обращения к концу 2026 (по документации Supabase) | В документах «публичный ключ (в ТЗ anon key)»; команды проверки используют заголовок `apikey` |
| 15 | Нет журнала действий админа | Если аккаунт админа украдут, будет не видно, что и когда меняли | Не добавлено (сверх ТЗ). Рекомендация в разделе «Остаточные риски» |
| 16 | `user_roles`: только чтение своей строки; `role default 'admin'` | ТЗ не говорит, кто может писать; значение по умолчанию `admin` небезопасно, если появятся другие роли | Политик записи нет вообще, прав записи нет: роль выдаёт только владелец в SQL Editor. Роль не хранится в токене, а читается из таблицы при каждом запросе, поэтому снятие роли действует сразу. `default 'admin'` оставлен как в ТЗ (единственная роль, запись только вручную); если появятся другие роли, значение по умолчанию надо убрать новой миграцией (записано в комментарии `001`) |
| 17 | Сид: десятый вкус Isida, у Capella «мускусный виноград» | В коде сайта (`src/data.js`) десятый вкус называется Auris (папайя), а у Capella «мускатный» | Засеяно по ТЗ, расхождения вынесены владельцу (вопрос 1), правки готовы ниже |
| 18 | Сид и безопасность | Правило «сид не запускается в проде» относится к тестовым данным | `004_seed.sql` это настоящий начальный контент для боевой базы: паролей и пользователей нет, повтор не дублирует и не затирает правки |
| 19 | Порядок вкусов и `updated_at` в сиде | В таблице нет колонки порядка, у десяти вкусов одинаковый `created_at`; `updated_at` у всех пусто (нигде не сказано) | `created_at` различается на миллисекунду по порядку из ТЗ, поэтому `order=created_at` даёт порядок ТЗ (тест `SD03d`). `updated_at` пуст, пока строку не меняли (это задокументировано в `docs/api.md`) |
| 20 | Двухфакторный вход админа | Украденный пароль админа даёт полный контроль над каталогом | В этой версии не навязывается (правила: предлагать, не навязывать; нужна поддержка в админке): HUMAN_ACTIONS.md, Шаг 1 (2FA аккаунта Supabase) и Шаг 2. Принудительное требование можно добавить политикой позже (решение владельца) |

Допущения без вопроса к владельцу: описание бренда и вкусов взято из ТЗ без добавлений; **`tagline` у всех вкусов пуст** (в списке вкусов ТЗ подписи нет, а `Discover Star` дано только как пример значения колонки; в более раннем черновике ТЗ из папки анализа эта фраза как слоган запрещена, а юридически чувствительный текст по умолчанию не публикуется; одна команда возвращает значение, см. «Готовые правки», вопрос 1); `nicotine_mg` пусто у всех (ТЗ значений не даёт); `working_hours` пусто; телефон, e-mail, адрес и координаты точки взяты из ТЗ без изменений, **координаты не проверялись**; максимальные длины текстов выбраны с запасом (4000 для описаний).

## Миграция и откат

- Миграции версионные и аддитивные (только создание). Повторный запуск любого файла безопасен, пока в проекте нет посторонних политик и вы не переименовывали ключи сида (проверено: все файлы подряд, затем только `001`, плюс проверка, что повтор `004` не затирает правки). `drop policy if exists` и `drop trigger if exists` относятся только к объектам, которые создаёт тот же файл. Оговорки: после добавления новых политик следующими миграциями повтор старого `002` остановится (список политик в самопроверке нужно обновить); `004` ищет строки по ключам.
- Откат до наполнения боевыми данными: удалить проект Supabase и создать заново (дешевле всего). Откат объектов вручную (`drop table … cascade`, `drop function …`) нужно решать отдельно и на живой базе агент его не выполняет.
- После наполнения любые изменения только новыми миграциями вперёд (`005_…`): сначала добавить, потом перевести сайт, удалять отдельным релизом по решению владельца.
- `002_rls.sql` и `003_storage.sql` заканчиваются самопроверкой: если защита собрана не так (платформа выдала лишнее право, на таблицах есть чужая политика, RLS на `storage.objects` выключен), файл откатывается с сообщением `GDS 002:` или `GDS 003:`. У `003` откатывается только часть 2, бакеты из части 1 остаются (без политик они безопасны). Что самопроверки действительно срабатывают, проверяют тесты `SC01`–`SC07`.

## Результаты проверок (на одноразовой базе, не на Supabase)

Автоматический набор `supabase/tests` (заглушка Supabase, SQL-тесты, блоки чек-листа):

- 376 различных проверок (идентификаторы уникальны, это проверяет сам запуск): структура и типы колонок, ключи и `on delete`, 25 CHECK и их поведение на плохих значениях, права на таблицы и колонки (включая `MAINTAIN` в PostgreSQL 17), точный набор из 25 политик, функции, матрица доступа (аноним, обычный пользователь, админ, подделанный токен и пустой `sub`), upsert и блокировки строк, Storage на заглушке, состояние между `001` и `002`, содержимое сида и порядок вкусов, нейтральность текстов (эвристика), идемпотентность, срабатывание самопроверок миграций, SQL-блоки чек-листа.
- Четыре круга на каждую базу: миграции по порядку, повтор всех миграций, повтор только `001`, повтор сида и самопроверки. Сверка, что набор проверок в кругах совпадает и совпадает с манифестом `expected-checks.txt` (удалённая или добавленная проверка не остаётся незамеченной).
- **8 прогонов:** PostgreSQL 17.10 и 15.18 × локаль `C` и `English_United States.1252` × режимы прав платформы «старый» и «новый». В каждом 1068 срабатываний проверок, **0 провалов**.
- **Мутационная проверка** (`supabase/tests/mutations.mjs`): 44 намеренные поломки. 36 поломок состояния базы (лишний `INSERT` у `anon`, публичная политика чтения, `is_admin` без `search_path`, выключенный RLS на таблицах и на `storage.objects`, чужие политики Storage, право на колонку, снятые ограничения и т.д.) и 8 поломок исходников миграций (`001` без RLS у таблицы, `001` со старым безусловным `revoke all`, `001` без отзыва `TRUNCATE`, сид без порядка вкусов, самопроверки `002` и `003`, переставшие останавливать файл). На чистой базе 0 провалов, каждая из 44 поломок делает красной хотя бы одну проверку (проверено на PostgreSQL 17.10 с локалью `C` и на PostgreSQL 15.18 с локалью `English_United States.1252`). Команда для воспроизведения в `supabase/tests/README.md`.

**Не проверялось** (нет живого проекта): настоящий Supabase (PostgREST, GoTrue, Storage API), коды HTTP-ответов, роль `postgres` без суперправ и право создавать политики на `storage.objects`, лимиты размера и типов файлов, публичные ссылки, поведение SQL Editor (окна подтверждения, смена роли на `anon`, откат блока `do` при ошибке), настройки Auth в панели, Security Advisor, резервное копирование и восстановление (в `embedded-postgres` нет `pg_dump`), PostgreSQL 16, локаль `en_US.UTF-8` на Linux (проверена только Windows-локаль `English_United States.1252`).

## Остаточные риски и последствия

1. **Нет журнала действий админа.** Рекомендация: миграция `005_audit_log.sql` с таблицей журнала и триггерами на пять таблиц (кто, когда, что менял; запись только триггером; читать только админ). Пока админ один, достаточно резервных копий и `docs/runbook.md`.
2. **Публичное API без возрастной проверки.** Возрастной экран сайта работает в браузере; данные каталога любой может получить с публичным ключом. Если юрист потребует иного, это изменение архитектуры (вопрос юристу в HUMAN_ACTIONS.md).
3. **Доступность `supabase.co` из России не проверена.** Я не нашёл подтверждения блокировки, но и проверки с российских сетей у меня нет. Проверить с домашнего и мобильного интернета до публикации. Страховка: сайт уже содержит данные вкусов (`src/data.js`); на сайте можно оставить их резервом.
4. **Бесплатный тариф Supabase.** По документации Supabase проект при низкой активности за 7 дней приостанавливается (восстановить можно в панели), ежедневных резервных копий на Free нет (на Pro 7 дней). Рекомендация: Free только для тестов, платный тариф к публичному запуску (вопрос 4).
5. **Персональные данные.** В базе единственные персональные данные: почта администраторов в Auth. Хранение за границей и правовые основания: вопрос юристу.
6. **Публичные контакты.** Телефон, почта и адрес точки читает любой владелец ключа и любой сборщик данных (так в ТЗ). Допустимость публикации на «информационном» сайте: вопрос юристу.
7. **Подтверждение почты выключено (так просит ТЗ).** Безопасно только при закрытой регистрации. Сброс пароля по почте работать не будет без настроенного почтового провайдера: пароль админа меняют в панели.
8. **Предупреждения Security Advisor** про `is_admin` и про две политики чтения ожидаемы (чек-лист, пункт 10).
9. **Нет собственных лимитов запросов.** Работают лимиты платформы.
10. **Роль миграций в песочнице суперпользователь, в Supabase это `postgres` без суперправ.** Различия в правах владельца на `storage.objects` на живой базе не проверены; если часть 2 `003_storage.sql` остановится с «must be owner of table objects», политики создают через панель по таблице из `docs/runbook.md`, раздел 10.
11. **Скрытие не удаляет файлы.** `is_active = false` скрывает строки базы, но не файлы в публичных бакетах и не кэш CDN (runbook, раздел 1).
12. **Одна учётная запись администратора и пароль без второго фактора.** Смягчается 2FA аккаунта Supabase, длинным паролем и мгновенным снятием роли.

## Готовые правки по ответам владельца

Выполняются в SQL Editor, только после ответа владельца. Не часть миграций.

Если правильно **Auris**, а не Isida (текст описания взят из `src/data.js`, подтвердить):

```sql
update public.products
set name = 'Auris', slug = 'auris', aroma_profile = 'папайя',
    description = 'Сладкий вкус душистой папайи.'
where slug = 'isida';
```

**После этой правки не запускайте `004_seed.sql` повторно, не поправив в нём десятую строку** (имя, slug, нота и описание): иначе повтор вернёт Isida отдельной строкой, и вкусов станет 11 (так же ведёт себя любое переименование ключа).

Если у Capella опечатка («мускусный» вместо «мускатный»):

```sql
update public.products
set aroma_profile = 'мускатный виноград',
    description = 'Цветочный профиль с белым мускатным виноградом.'
where slug = 'capella';
```

Если юрист и владелец решат, что подпись `Discover Star` у вкусов публиковать можно (в сиде она пуста):

```sql
update public.products set tagline = 'Discover Star' where line = 'Stellar';
```

Если нужно вернуть каскад как в ТЗ (удаление бренда или категории стирает вкусы; не рекомендуется):

```sql
alter table public.products drop constraint products_brand_id_fkey;
alter table public.products add constraint products_brand_id_fkey
  foreign key (brand_id) references public.brands (id) on delete cascade;
alter table public.products drop constraint products_category_id_fkey;
alter table public.products add constraint products_category_id_fkey
  foreign key (category_id) references public.categories (id) on delete cascade;
```

Если нужно вернуть публичный список файлов, как «SELECT всем» в ТЗ (не рекомендуется: виден список всех файлов, в том числе неопубликованных):

```sql
create policy gds_storage_public_list on storage.objects
  for select to anon, authenticated
  using (bucket_id in ('product-images', 'brand-logos'));
```

(После этого самопроверка `003` при повторном запуске и пункт 4 чек-листа остановятся на «посторонней политике»: это ожидаемо, придётся внести имя политики в список разрешённых в `003`, часть 2, и в пункт 4.)

Если вкусы скрытого бренда должны оставаться публичными, как буквально в ТЗ:

```sql
drop policy products_public_read on public.products;
create policy products_public_read on public.products
  for select to anon, authenticated using (is_active);
drop policy product_images_public_read on public.product_images;
create policy product_images_public_read on public.product_images
  for select to anon, authenticated
  using (exists (select 1 from public.products p where p.id = product_images.product_id and p.is_active));
```
