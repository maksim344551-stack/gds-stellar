## Шаг 2. Закрыть регистрацию и настроить вход (до создания админа)

Откройте слева **Authentication**, раздел **Sign In / Providers** (в старых версиях: Providers и Settings).

- [ ] **Allow new users to sign up** (разрешить регистрацию новых пользователей): **выключить**. Зачем: иначе любой посетитель сайта сможет завести учётную запись (прав записи у неё не будет, но лишний мусор и риск занять ваш адрес раньше вас). Админа вы создадите вручную на Шаге 5. *Это моя рекомендация; ТЗ про это молчит (вопрос 2 в отчёте).* Если оставить включённой, ничего не сломается, но пропадает важная защита.
- [ ] **Allow anonymous sign-ins** (анонимные входы): **выключить**.
- [ ] Провайдер **Email** должен быть включён (вход по почте и паролю).
- [ ] **Confirm email** (подтверждение почты): **выключить**, как просит ТЗ. Это находится внутри настроек провайдера Email. Что это значит: письмо подтверждения не требуется. Это допустимо только при закрытой регистрации (см. выше). Письма из Supabase по умолчанию ограничены, поэтому подтверждение через почту без настройки собственной почтовой службы всё равно работало бы плохо. Забытый пароль админа письмом не восстановить, пока вы не подключите свою почтовую службу; пароль можно сменить в панели (Authentication → Users).
- [ ] Минимальная длина пароля: **12** или больше (в настройках провайдера Email, если такой пункт есть). Защита от паролей из известных утечек (Leaked password protection), по документации Supabase, доступна на платных тарифах: включите, если перейдёте на платный.
- [ ] Двухфакторный вход для самого админа (TOTP) в этой версии не навязывается: он требует поддержки в будущей админке (сайт должен предложить подключить приложение-аутентификатор). Пока админ входит только по паролю, важно, чтобы пароль был уникальным и длинным, а аккаунт Supabase был защищён (Шаг 1). Принудительное требование «второй фактор обязателен» можно добавить политикой позже (решение владельца).
- [ ] Нажмите **Save changes** на каждой странице, где вы что-то поменяли.
- [ ] По желанию (меньше лишней поверхности): **Database → Extensions**: если включено расширение `pg_graphql` (GraphQL API), а оно сайту не нужно, выключите его. Realtime для таблиц каталога не включайте.

## Шаг 3. Выполнить миграции по очереди

Файлы лежат в папке проекта: `C:\Users\maksi\Projects\gds\supabase\migrations\`. Открывайте их в **VS Code** (в Блокноте русские комментарии могут показаться «кракозябрами», это только вид, но лучше VS Code).

Для **каждого** файла по порядку (001, 002, 003, 004):

1. [ ] Откройте файл, нажмите Ctrl+A, затем Ctrl+C.
2. [ ] В Supabase слева **SQL Editor**, кнопка **New query**, вставьте (Ctrl+V).
3. [ ] Нажмите **Run**.
4. [ ] Внизу должно появиться **Success. No rows returned**. Если появилась красная ошибка: **не запускайте следующий файл**, скопируйте текст ошибки и пришлите мне. Сообщения вида «GDS 002: …» или «GDS 003: …» значит, файл сам остановился, потому что защита собралась бы не так (например, в проекте есть чужая политика, созданная вручную по шаблону из панели; сообщение назовёт её), и этот файл (у `003` его вторую часть) не применил.

Если редактор покажет окно вроде «потенциально опасный запрос» (из-за слов `drop policy if exists`, `drop trigger if exists`, `update`): в файлах `drop` касается только политик и триггера, которые тот же файл сразу создаёт заново, данные не удаляются. Подтвердите запуск.

Порядок и что делает каждый файл:

- [ ] `001_init.sql`: создаёт 6 таблиц и сразу закрывает их (RLS включён, политик нет, значит доступа ни у кого нет). Проверка: **Table Editor** показывает `brands`, `categories`, `products`, `product_images`, `stores`, `user_roles`.
- [ ] `002_rls.sql`: права и политики. Проверка: в Table Editor рядом с таблицами нет предупреждения «RLS disabled».
- [ ] `003_storage.sql`: два файловых бакета и их защита (внутри две части: бакеты и политики; если остановится вторая, бакеты уже созданы). Проверка: Шаг 4.
- [ ] `004_seed.sql`: бренд, категория, 10 вкусов, точка продаж. Проверка: в Table Editor в `products` 10 строк, в `brands` 1, в `stores` 1.

Повторный запуск: каждый файл можно запустить повторно, ничего не продублируется и данные не сотрутся (на одноразовой базе это проверено, в том числе повтор одного `001` отдельно). Но: `004_seed.sql` ищет строки по ключам (имя бренда, slug вкуса и категории, название и адрес точки), поэтому если вы переименовали такой ключ, повтор вернёт строку под старым ключом; а когда в проект добавят новые политики следующими файлами (`005_…`), повтор старого `002` остановится с сообщением о «посторонних политиках». Поэтому: запускайте каждый файл один раз, повтор нужен только если файл остановился с ошибкой.

**Никогда не запускайте в Supabase файлы из папки `supabase\tests\`.** Это тестовая заглушка для проверок на одноразовой базе, она не для вашего проекта (она защищена от случайного запуска, но не пробуйте).

## Шаг 4. Проверить Storage (файлы)

- [ ] Откройте **Storage**. Должны быть два бакета: `product-images` и `brand-logos`, оба с пометкой **Public**.
- [ ] Откройте настройки каждого бакета (иконка карандаша или «Edit bucket»): лимит размера файла **5 MB** у `product-images` и **2 MB** у `brand-logos`, разрешённые типы: `image/jpeg, image/png, image/webp, image/avif`.
- [ ] **Storage → Settings**: общий лимит размера файла проекта не меньше 5 MB. (Если общий лимит меньше лимита бакета, действует меньший.)
- [ ] Правило имён файлов (его проверяют политики, когда загружает админ через сайт или админку): `product-images/<slug-вкуса>/<uuid>.<расширение>` и `brand-logos/gds/<uuid>.<расширение>`; расширение маленькими буквами из `jpg, jpeg, png, webp, avif`. Загрузка прямо в панели Storage этим правилом, по моим сведениям, не ограничена (на живом проекте не проверено), но придерживайтесь его, чтобы будущая админка видела файлы единообразно.
- [ ] Проверку публичной ссылки сделайте по `docs/backend-security-checklist.md`, пункт 4.

## Шаг 5. Создать админа

Админ (роль `admin`) нужен для будущей админки на сайте. **Править каталог вы можете уже сейчас без него**: в Table Editor панель работает с правами владельца.

- [ ] **Authentication → Users → Add user → Create new user.**
- [ ] Email: ваш рабочий адрес. Password: уникальный, 12+ знаков, из менеджера паролей. Отметьте **Auto Confirm User**. Нажмите **Create user**.
- [ ] В списке пользователей откройте созданного и скопируйте его **User UID** (длинный идентификатор вида `3f2b9c1e-…`).
- [ ] В **SQL Editor** выполните (замените `UUID_ПОЛЬЗОВАТЕЛЯ` на скопированный идентификатор, **кавычки оставьте**):

```sql
insert into public.user_roles (id, role) values ('UUID_ПОЛЬЗОВАТЕЛЯ', 'admin');
```

- [ ] Проверка: выполните

```sql
select u.email, r.role from public.user_roles r join auth.users u on u.id = r.id;
```

Должна быть одна строка с вашей почтой и ролью `admin`. Если вы видите чужие адреса: не выдавайте им роль, удалите их в Authentication → Users.

- [ ] Второго пользователя без роли (обычного) создайте так же и только если собираетесь делать проверку 3 «по-настоящему» (чек-лист); потом удалите.

Снять права админа позже: `delete from public.user_roles where id = 'UUID';`. Действует сразу.
